# 微信消息可靠交付：持久化 Outbox / 单账户发送所有权

日期：2026-09-18（+08:00）  作者：ChatGPT  状态：已实现并完成本地故障测试，待宿主集成与微信 canary 验收

**不要把本报告理解成已经上线。没有连接生产服务器，没有重启网关，没有替老板补发历史消息。**

评估基线：`Lyric8/gpt@148b577f3616cb4da837351e238c8221cf705341`，目录 `notify-reliability/`。
交付代码：`implementation/`。不包含配置凭据、数据库副本、原始回复正文或账号密钥。

## 1. 裁决

推荐一个方案：**在现有 state.db 中扩展持久化 Outbox，接管全部微信发送；网关与自动化只提交交付意图，由同一账户的唯一 worker 完成实际发送。** 不引入 Redis、RabbitMQ，也不额外部署竞争性的微信补发器。

必须废止“对话回复不做持久化兜底”的旧约定。重复发送的根因不是持久化，而是同一意图由多个没有共同身份和回执的发送者负责。这里对话回复不再先直发、失败后复制到另一条队列，而是第一次发送就从唯一 Outbox 出发。

保证从**成功提交本地事务**开始：正文、分片进度、附件快照不会因为限流、进程重启或超过重试次数而被遗忘；未完成内容不按年龄或队列上限删除。前提是本地存储没有丢失、SQLite/文件系统按配置提供持久化、所有发送者遵守单一所有权、故障最终解除且消费能力足够。

不能承诺：微信永久封禁后仍必达、磁盘无法提交时仍“已经保存”、平台返回成功就代表老板已看见、没有服务端幂等契约时实现端到端恰好一次、微信完全不可用时仍立即通过微信告警。这些不是多加几次 retry 能解决的问题。

## 3. 架构与状态

```text
微信输入 -> Agent 生成最终回复
                 |
                 v
         提交原文 + 稳定交付意图身份
         ready=0（禁止抢先发送）
                 |
         生成不可变交付计划
         文本分片 + 本地附件字节快照
                 |
         清除本次已生成回合的 resume_pending
         ready=1
                 |
自动化 --显式事件 key--> 同一个 state.db / wx_outbox_*
旧文件队列 --只入库、不直发--^
                 |
        账户级 POSIX flock 唯一 worker
        持久化 not_before / 逐片 nonce
                 |
        受检 HTTP + iLink 业务回执
          /          |             \
       accepted     retry          blocked
       下一片      等待后补发       内容保留 + 告警 + 修复
          |
    所有物理部分 accepted
          |
    父交付 accepted（只表示平台接受）
```

父状态：`preparing / queued / blocked / accepted`。`ready=0` 是独立的恢复屏障，不是送达状态。子状态：`pending / sending / retry / blocked / accepted`。

**Outbox** 是存储交付义务的数据结构，不是网络发送成功的同义词。**幂等键** 标识一次业务事件：最终回复使用账户、传输 profile、会话和入站 message_id；通知调用者必须提供 job/run/event key。不同事件即使正文相同，也不能按正文哈希全局去重。

同键不同正文不覆盖旧记录：第二份内容保存为 blocked 冲突记录，禁止用普通 `resume` 自动释放。缺失入站身份也保存原文并 blocked，不直接扔掉已经生成的报告。

## 4. 限流、重复与附件的精确语义

每个账户默认物理消息间隔 20 秒。这是保守初始参数，不是宣称微信公布了固定“每 20 秒一条”配额。第一次无积压的短回复不额外等 20 秒；后续片段、附件、通知共同排队。

HTTP 429 和真实频率错误 `-2` 进入账户级冷却，至少 30 秒；HTTP `Retry-After` 的秒数或日期优先，900 秒不会被本地 300 秒退避上限截断。指数退避和抖动补充处理连续失败。所有这些截止时间在数据库里，重启不会清空。

`-2` 且 `errmsg=unknown error` 按提供的适配器契约是会话异常，不能按普通限流盲重试。身份失效、未知 ACK 结构暂停该账户；明确内容拒绝阻塞该条。操作员修复后执行 `resume`，不会重发已确认部分。

**未知 ACK 不允许无限重试刷屏。** 当前实现要求发送回执有明确的整数 `ret=0` 或 `errcode=0`，且没有非零业务码。若实际成功回执省略所有状态码，默认 blocked 并暂停账户，必须先用真实 canary 核实官方/实际契约再明确放行。上传准备响应可用必要的 URL/ticket 字段验证成功，但这不是聊天消息的送达回执。

确认过的部分不重发；失败的附件不会让正文重新发送，正文成功也不会让整条交付被误记完成。本地附件在交付前复制为 SQLite BLOB，原临时文件之后删除不影响补发。当前安全限制为单附件 32 MiB、单交付附件合计 64 MiB；超过限制 blocked 并保留原文，不冒充成功。

每个物理发送使用稳定 `client_id`。但提交请求后响应丢失，或平台接受后进程在写本地 ACK 前被杀，仍可能出现重复。恢复设置 `ambiguous=1`；文本第一次发送就带稳定短编号，重放编号不变。**这实现本地幂等入库和有记录的至少一次尝试，不声称微信端恰好一次。** 文件重新上传会产生新的临时加密/CDN材料，不能假定相同 client_id 与不同材料一定被服务端去重。

## 5. 所有权与旧系统的关系

不是三套队列叠加：新表成为微信唯一交付真相。`delivery_obligations` 保留给其他平台和旧记录审计。安装器从旧启动/运行时重放查询中排除微信，防止两个恢复引擎同时负责同一条义务；同时把旧 `_prune` 限定为只删终态。

历史微信失败项经人工选择后，在**同一个 state.db 事务**中创建新义务，并把原状态改为 `outbox_managed`。新义务完整 accepted 后，原状态同步改为 delivered。切换前必须停止网关及旧 sender，检查选中的会话不存在应当继续执行的较新未完成回合；禁止不核对会话就清除 resume 标志。

旧 `notify-queue/*.txt` 只作为兼容入口，采集器把它们幂等纳入数据库，绝不自己调用 `hermes send`。`.part` 非零或损坏的历史文件需要显式接受“全量补发可能重复”；文件不会自动删除。`outbox/*.staged` 不再依赖日志判断成功，保留待人工核对。

旧 `campfire-sender.service` 必须持续停止并禁用。自动化新代码优先调用 `wx_outbox_cli enqueue --key ...`；旧脚本的入队接口暂时仍可用，由兼容采集器接管。cron 采集扫描激活水位之后的**全部不可变输出文件**，不只检查每个 job 最新的一个文件。

`send_weixin_direct` 及适配器公开发送方法被重定向到 Outbox；旧 `_send_with_retry` 不会把“已入库但未确认”再转成纯文本兜底。裸底层旧发送函数在可靠模式下拒绝调用。没有配置、损坏配置、把 enabled 改成 false，都不能在运行中偷偷退回双发送者模式。

## 7. 运维可见性与告警边界

网关 worker 每 5 秒持久化心跳。独立 systemd timer 每 20 秒检查：心跳超过 30 秒、队列最老项超过 120 秒、blocked、账户暂停、可用磁盘不足 512 MiB、明显时钟回拨。异常退出码为 2，systemd unit 失败并留在 journal。

延迟/阻塞交付会生成一条合并状态通知，同一账户 10 分钟内合并一次，通知不会对自身再告警。若微信仍不可用，它也只能留待恢复后发送；它不是旁路保障。

**本交付没有冒充已配置独立远程告警。** 上线的必要运营门槛是：把 watchdog 的失败接入现有独立监控或 Hermes 的 GitHub/直接对话控制面，并实际演练微信断开时另一执行者仍能发现故障。仅有本机 journal 不能保证主机宕机时老板或操作员被及时叫醒；现有 GitHub 控制面可保持老板继续只用微信。不能把“本机已经有告警记录”说成“老板已收到告警”。

处理完成回调表示 Agent 生成和持久化交接完成，不能拿它当微信送达回调。交付状态从 `wx_outbox_cli status` 查询；`accepted` 也不是已读。

## 8. 支持范围和上线门禁

本版本覆盖最终文字回复、本地报告/文件/图片/视频附件、现成音频文件，以及自动化通知。为了避免随意下载和持久化临时 URL，远程图片明确降级成“图片链接（未作为附件投递）”，不会悄悄删掉。需要原生远程图片时，生产者先下载到经过验证的本地文件再提交。

接管最终回复会绕开旧的“最终阶段自动生成 TTS”步骤。**上线前必须确认当前微信会话没有依赖 auto-TTS；否则本版本不能直接替换该功能路径。** 已生成的音频附件正常持久化发送。不隐瞒这项兼容范围。

本地回归使用 CPython 3.13；源码另外经过 Python 3.11 语法检查。尚未宣称在宿主 Python 3.11/Hermes 完整依赖图上通过运行验收。真实宿主必须执行同一套测试、安装器 check、模块导入验证、恢复屏障验证和真实微信 canary；详细命令见 `RUNBOOK.md`。

## 9. 存储、延迟、复杂度

SQLite WAL + FULL 同步用本地提交换取持久性；网络请求不在数据库事务内。单机账户用内核 flock，不用会过期的租约假装能撤销旧进程：旧进程被 SIGSTOP 后仍持锁，新 worker 不能越过它发送。数据库子项 nonce 防止陈旧 ACK 覆盖新状态。取消时等待已有数据库线程退出，再释放锁。

20 秒间隔意味着稳态约 3 个物理消息/分钟；4 片正文加 1 个附件，无其他积压时，第 5 个发送开始至少在第 1 个之后 80 秒，另加上传、网络、冷却时间。输入持续超过输出能力时队列会增长，不能一边限速一边承诺零等待。短摘要加报告文件可以降低长篇拆片数，但不能自动删掉原正文。

每小时尝试清除完整 accepted 超过 7 天的正文/附件载荷，保留幂等身份墓碑；未完成内容永久保留直到明确修复/人工处置。SQLite 空闲页可复用，不承诺文件立刻缩小；不要在活跃网关上自动 VACUUM。需要主机故障级保障时用 SQLite 在线备份和既有加密备份策略；不能把单块磁盘持久化等同于异地灾备。
