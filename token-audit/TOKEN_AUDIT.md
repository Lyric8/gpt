## 三、我判断的消耗结构（请评估是否成立）

1. **最大头：单次 API 调用的上下文体积**。主会话上下文约 250K~270K tokens，而**每一个工具调用迭代都会把整个上下文重发一次**（靠 prompt cache 打折，但 cache read 仍计费）。1,321 次调用 × ~267K ≈ 353M 缓存读 —— 与我实测的 354M 吻合。
   - 推论：**成本 ≈ 调用次数 × 上下文体积**。把上下文从 267K 压到 60K，理论上省 ~4.5 倍；把每次回合的调用次数从 12 降到 5，再省一半。
2. **次大头：定时任务把 agent 当脚本用**。收件箱轮询每 5 分钟跑一次，每次运行 24~86 次 API 调用、缓存读 2.3M~9.3M。47 次运行就吃掉 78.9M 缓存读。
3. **行为习惯放大**：
   - 我习惯"一次工具调用做一件事"，且不少调用是为了**重复确认**（例如反复 ls/读同一文件、反复验证已确认的结论）；
   - 大块原始输出直接进上下文（日志 tail、表格、脚本全文），而不是写成文件后只读需要的片段；
   - 长会话不重置，导致固定上下文随对话无限增长（本会话已积到 5,600+ 条消息）。

## 四、我的工作流（请据此评估，而不是只看数字）

- **常驻任务**（cron，`~/.hermes/cron/jobs.json`）：
  - 收件箱轮询（每 5 分钟，agent，有变更检测）：读仓库 `chat` 分支的交接消息 → 领租约 → 干活 → 回执 + 完成标记 + 账本行 → 通知老板。
  - 发布兜底（每 1 分钟，agent，有变更检测）：盯 Release/部署是否异常。
  - 取回 GPT Pro 答复（每 10 分钟，agent，一次性）：只读浏览器，把 ChatGPT 网页版答复取回落盘。
  - 发送者崩溃自修（每 10 分钟，agent，有变更检测）。
  - 纯脚本人（no_agent，几乎零 token）：slot 轮换检查（每 30 分钟）、回复救生员（每 2 分钟）。
- **对话侧**：老板用微信跟我聊；我每回合往往要：查证 → 改脚本 → 实测 → 复核 → 写回执/账本 → 回话。多数回合会做 10~20 次工具调用。
- **跨执行者协作**：与 ChatGPT（网页版 Pro / 定时任务）通过 GitHub 仓库 `chat` 分支交接；我负责服务器侧与部署。
- **状态落盘优先**：状态、账本、队列、租约都在文件/DB 里，而不是靠对话记忆。

1. **优化方案（要可落地、要数字预期）**：针对"调用次数 × 上下文体积"这个成本结构，给一套具体的省 token 做法（含：上下文预算、工具调用编排、结果裁剪、缓冲/去重、缓存友好性）。

4. **会话生命周期**：什么时候应该开新会话、如何把状态在会话之间传递而不把历史塞进上下文。
