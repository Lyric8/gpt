# Hermes 工作流 token 五倍压降：实施裁决与验收方案

版本：1.0　证据主题：2026-09-18 token audit　作者：ChatGPT

交付状态：控制核心与本地测试已完成；未接入生产 Hermes 网关，未完成线上 A/B。生成本包时 GitHub 连接器仅开放读取，容器无法解析 GitHub，因此当时没有远程提交。`bin/publish.py` 在拥有现有 GitHub 认证的服务器上执行，成功后打印实际代码/交接提交；只有该结果可以证明已推送。本文中的节省比例均为测算，不是实测节省。

## 0. 裁决

建议采用 **“确定性脚本执行和验证 + 小上下文决策 + 持久化请求预算”**，不换弱模型，不减少验证项目，不靠延长轮询间隔达标。

以原始明细的 **443.90M gross tokens** 为同等工作量基线，保守情景预计 **83.736M，保留 18.86%，约 5.30 倍压降**；目标情景 **46.539M，保留 10.48%**。这些数字依赖明确的平均上下文和请求数条件。只设置 64K 上限、实际请求数不下降时，压力情景仍消耗 **124.696M，保留 28.09%，不达标**。

预算到顶后暂停并持久化，能够避免静默丢任务和未经验证的副作用，但并不自动证明可用性/完成时延没有退化。必须同时通过完成率、积压量、通知交付和延迟验收，才能声称“没有牺牲可靠性”。任意复杂任务的 token 需求不存在可由这个账本证明的统一五倍上界。

`cron-jobs.md` 实际列出 **5 项 agent 任务**：收件箱、发布兜底、发送者修复、8 分钟取可靠性答复、10 分钟取另一答复。后两个没有变更检测，其余三个已有检测。已有检测节省的空轮询不能再算一遍；被唤醒后的真实开发工作也不能伪装成“轮询开销”。

### 1.1 正确成本模型

对请求 j 记非缓存输入 U、缓存读 R、缓存写 W、输出 O：

```text
prompt_j = U_j + R_j + W_j
traffic  = Σ(prompt_j + O_j)
cost     = Σ(pU_j·U_j + pR_j·R_j + pW_j·W_j + pO_j·O_j)
           + 按次收费 + 外部工具成本
```

Hermes 核对版本 `693641aa` 的 `CanonicalUsage` 就采用分离口径。直接读某供应商原始 `prompt_tokens` 时，缓存可能已经包含在其中，不能照搬再加。

“上下文 × 调用次数”是 **输入流量** 的一阶近似，不是完整美元成本公式。上下文随每轮增长 g 时，输入近似 `N·S + g·N·(N−1)/2`。API 的物理请求、模型推理迭代、工具调用条数是三个计数器：一次模型响应可包含多个工具调用，SDK 重试又可能产生更多物理请求。

缓存读占输入 99% 不代表占费用 99%。若仅作敏感性演算，假设非缓存单价为缓存读的 50 倍，未命中率从 1% 升至 5%，单位输入加权价格会从 1.49 升至 3.45 个缓存价格单位。输入压到 20% 时，输入费用仍可能保留约 46.3%。这是演算，不是用户的已确认费率。

本次预测保留全部原输出 token，更不能据此保证美元也缩为五分之一。生产须分开验收 gross tokens、各桶 token、实际账单/套餐配额；模型路由、报价版本、费用来源必须一起记录。

## 2. 目标工作流：模型不再担任轮询器和逐条命令调度员

```text
定时器 / 用户消息
    ↓
零模型观察器：取版本、判断语义变化、查本地待办
    ↓
持久事件队列：事务落盘 + 唯一事件键 + 重试时间
    ↓
确定性协调器：取得现行 Git 消息租约 / 必要资源租约
    ├─ 已完成：读回外部证据，补缺回执/账本/通知，不重做业务
    ├─ 已知操作：运行固定 runbook + 完整测试/读回
    └─ 需要判断：建立独立 task capsule，按角色小上下文进入模型
                          ↓
                     持久预算准入器
                          ↓
                    有界决策 / 批量工具
    ↓
独立验证 → 远端回执与 completion 核对 → 账本对账 → 通知 outbox
```

Git 队列仍是跨执行者权威；本包的 SQLite 事件表仅是本地调度日志，不能替代现行 message lease、resource lease、Git blob CAS，也不改变 v3 文件名、完成和接管协议。

当前 `chat/README.md` 要求轮询时读取最新协议和状态。脚本每次取得同一 Git 快照中的版本并做确定性检查，旧内容只有版本相同才可复用；这不等于把旧文本永远当最新。协议 blob 改变时本包观察器报错并停推进游标，需要复核新协议，不会盲目继续。首轮不发明历史 baseline，全部源消息先交由确定性完成记录对账器判定。

## 3. 请求预算：限制的是物理请求，而不是随口写一句“少调用工具”

K 按 1,000 token 计。所有上限包含 system/developer、工具 schemas、当前需求、状态、历史、工具结果，以及供应商实际发送格式引入的计数。

| 角色 | 平均输入目标 | 单请求输入硬上限 | 单分段请求硬上限 | 根任务请求/分段上限 |
|---|---:|---:|---:|---:|
| 观察/健康探针/已知修复/通知发送 | 0 | 0 | 0 | 0 |
| 日常对话/运维决策 interactive | 32～40K，48K 触发整理 | 64K | 8，目标 4～6 | 24 / 3 段 |
| 未知异常 incident | 12～16K | 24K | 4 | 8 / 2 段 |
| 明确的工程实现 engineering | 40～48K | 64K | 12 | 36 / 3 段 |

根任务累计输入预算分别为 interactive 1.024M、incident 128K、engineering 1.536M；输出累计预算分别为 160K、48K、384K。单请求输出预留上限分别为 8K、8K、16K；实际还必须满足供应商真实 context window。输出上限包括供应商计入输出的推理 token，不能仅用最终可见文字估算。

这些值是上线初始策略，不是模型能力参数。工程任务需要完整长代码、长推理时，用工程角色和文件写入路径处理，不把代码截成不完整内容、不私自降低思考强度；仍不能把 `finish_reason=length` 当成功。任务确需更高预算时，先产生可见升级请求，明确增加额度并审计，不能偷换 task_id 清零。

### 3.1 准入与超额动作

每次真正调用供应商之前，事务预留一次请求及输入/输出额度。SDK 内部重试必须关掉，调用方显式的每个重试也经过准入器；同任务的摘要、辅助调用、fallback 使用同一个根任务 ID。不能只接主模型然后让辅助模型绕行。

若超过 48K 软阈值，在已完成工具组后的安全边界：先持久化完整记录，整理已验证状态和证据索引，再重建上下文。超过 64K 则 **不发送请求**，不等待供应商超窗报错再继续扣费。强制动作顺序：

1. 原始需求、约束和当前工具事务保持完整；原日志/代码/浏览器复制文本先持久化。
2. 大工具结果替换为结构化 manifest 和哈希引用，按失败 ID 定点读取。
3. 只移除有 checkpoint 覆盖的完整已结束回合；有依赖的 assistant/tool 组不可拆。
4. 整理后仍超限，保存任务胶囊，切换同根任务的新分段；原输入以不可变引用按模块读取。
5. 分段或根任务额度用尽，标 `WAITING_BUDGET` 并产生可靠通知，不写业务 completion，不静默消失。

进程崩溃留下的 `IN_FLIGHT` 请求必须先对账；无法确认 usage 的请求保留完整预留额度，不能当“失败没花 token”。重新开会话、重新登录、重新启动网关都不得重置根任务预算。

### 3.2 计数器不能伪精确

中文字符数/4、字节数/4、只数 message 文本、只用被裁剪的生命周期 hook 都不够。读到的 Hermes hook 实现会限制 payload 大小，不适合做完整发送体的硬拦截。

准入点必须位于全部供应商转换完成之后。使用已确认的目标 tokenizer/chat template，包含工具 schemas 和特殊 framing，并与真实 provider usage 对齐。视觉、音频、缓存写等特殊路径另行计数。未确认的路径可以先做 shadow 观测，但不得假冒“已认证硬限制”。本包 `TokenCount.certified_upper_bound` 默认 false；没有可靠计数器时严格发送被拒绝。抽样比对是发现误差的方法，不是对所有未来输入的数学证明；需已知编码规则或可证明保守上界作为基础。

## 4. 上下文组成、结果裁剪、缓存策略

48K 工作上下文的初始预算分配为：固定安全/行为规则 6K、角色工具 schemas 6K、状态胶囊 4K、当前原始请求 4K、最近相关完整回合 8K、相关源码/证据片段 12K、预留 8K。这不是逐栏截断命令；某项不可分的必须内容超额时，重分配或分段，不能删除用户约束。

系统提示只保留稳定规则；技能目录摘要稳定，任务需要时才加载对应技能正文；每个角色选固定工具集合，不把所有浏览器、媒体、运维工具 schemas 常驻每轮。任务中途必要时可换工具角色，但把此举视为一次上下文 epoch 重建，不能每一轮随机抖动工具顺序。

单工具可见结果目标 512～1,500 tokens、硬预算 2K；一个批次进入模型的结果合计不超过 8K。命令的原始 stdout/stderr 先落盘，返回命令 ID、退出码、完整/截断标志、成功/失败数量、失败项、文件哈希及读取入口。超过限制的结果不得先 `tail` 掉再假装持久化了完整证据。分页必须携带 total/next，清单漏页视为失败。

`run_read_batch` 把独立只读检查并行成一轮工具往返，默认最多 4 个并发、每批最多 67 项；每个检查仍有独立退出码和结果。它不是沙箱，声明 `independent_read_only=true` 不是能力隔离，调用列表必须经过既有命令审批。涉及副作用的顺序工作不走这个并行器。

错误摘要不能仅取 stderr 最后几行；完整失败 ID 列表、失败总数必须由机器汇总。失败过多时保留总数及索引并分段读取，不把前 N 个通过误当全量通过。`batch.py` 的输出配额是每 25ms 观察到超限后终止进程，可能短暂超出；生产还需文件系统配额或 cgroup/独立分区约束，不能把它宣传成绝对磁盘硬上界。

读取缓存键至少包括：资源身份、source blob/commit SHA 或内容 SHA-256、命令/检查器版本、参数、环境指纹。缓存只复用不可变快照的结果。部署状态、租约到期、进程存活、权限变化等实时事实必须重新探测，不能沿用旧 PASS。

Prompt cache 依赖共同前缀；一个 epoch 内固定前缀并追加，epoch 边界才整理。时间戳、队列深度、临时状态放动态尾部，不写进系统提示最前面；不要每轮重新生成摘要导致前缀频繁变动。也不要为了维持 99% 命中率继续携带 267K 的无关历史。保留旧大缓存并不是最优目标，总代价才是。

本包全量 artifact 为本地 0600 文件、专用目录 0700；原始 prompt/日志可能有敏感数据，运行态目录不得提交 GitHub。加密、留存清理和脱敏必须服从现有环境政策；未完成任务引用的数据不可被 GC 清除。

## 5. 工具编排：保留检查，减少模型往返

正常变更按以下 4～6 次模型请求组织，而不是让模型逐条“下一步跑什么”：

| 阶段 | 模型职责 | 程序职责 |
|---|---|---|
| 1. 取证与判断 | 一次决定本任务需要的相关证据和改变范围 | 批量取元数据、变更、依赖、必要日志，生成 manifest |
| 2. 实现决策 | 基于证据生成完整源码/受控操作规格 | 保存文件，校验输入版本与操作前置条件 |
| 3. 验证 | 只对真实失败判断根因；全通过则无需“再想一遍” | 全套必需测试、静态检查、协议校验、缺项校验 |
| 4. 条件修复 | 仅失败分支消耗 1～2 次额外请求 | 重跑受影响测试 + 规定回归范围，不伪造 fresh PASS |
| 5. 提交与交付 | 解释结论和未解决风险 | CAS 提交、远端读回、completion/账本对账、通知出队 |

测试独立于模型写的总结。高风险设计审查、未知根因判断、隐私/权限判断不能一律降格为字符串匹配；只有确定性的重复复核才自动化。更快不是免除思考和代码评审。

## 6. Cron 改造表

保留原有检测时延，不靠降低检查频率省 token。成本降幅指该任务的模型 token，且要求工作量可比；复杂业务处理归到原事件根任务，不能换桶藏消耗。

| 任务 | 新触发/间隔 | 正常路径请求 | 未知异常预算 | 预计模型 token 降幅 |
|---|---|---:|---:|---:|
| 收件箱 f0297666a04f | 保留每 5 分钟；HEAD 快筛 + 仅 source path/blob 语义差异 + 独立 pending drain | 0；业务判断另建小上下文 | 4/段、8/事件；真正开发转 engineering 并仍计入原事件总账 | 管理+处理合计约 81～95%，不是承诺所有业务零模型 |
| 发布兜底 c73de63b1c2d | 每 60 秒探测部署健康和部署 SHA；Release 未变也探测健康 | 0 | 4/段、24K 输入硬上限；同一事故仅一个活动根任务 | 90～99%（已知发布/回滚流程可脚本化时） |
| 取可靠性答复 + 另一取答复 | 保留原 8/10 分钟；只在 outstanding request 存在时启动；截止时间到则可见告警 | 0 | 未知网页状态一次受控升级，最多 4/段；不是反复模型盯网页 | 95～100%（机器可验证交付/受控复制稳定时） |
| 发送者崩溃修复 4259af716b7c | 保留 10 分钟脚本检查，优先 systemd 进程监督 | 0 | 未知反复崩溃合并成一次 incident | 95～100%；该项原来绝对量很小 |
| slot 轮换/回复救生员/周检查 | 保留现有 no_agent；依然校验和告警 | 0 | 只有未覆盖的新故障才升级 | 原本接近 0，不重复认领收益 |

发送者每 20 秒和回复救生员每 2 分钟的可靠交付机制不能合并成模型任务，更不能因为主任务超预算而暂停补发。进程重启自动恢复应有退避和尝试上限，例如 15 分钟最多 3 次，超过后保留队列并告警；具体执行遵守现有服务启动限制和幂等恢复。

关键机制：

- **变化不等于新任务**。Git HEAD 会因自己的回执、账本和租约写入而改变。最终去重键必须是源消息路径+blob 和当前 completion；自写 HEAD 不能再次唤醒同一业务。
- **没有变化不等于无待办**。未到 retry_at 的失败消息、过期租约、未完成通知需要独立待办扫描。不能只在 HEAD 变化时 drain。
- **检测器报错不等于没变化**。网络、分页、权限、协议改变、DB 错误需可见异常且不得推进确认游标。`no_agent` 的失败应由独立脚本健康监控处理，不依赖“模型读一下报错”。
- 收件箱扫描只登记，不执行外部副作用；批量最多登记 20 个新候选/协调批次、相关事故 30 秒合并窗口，保留全部事件身份及未处理部分游标。紧急通知不经过该合并窗口。对于本包的全量观察器，暂未实现该分页限额，部署前可由既有协调器限制领取数；不得把代码宣称为已经具备分页批扫。
- 本环境浏览器仅允许点击/复制/粘贴。不要用 DOM/内部接口绕过限制。优先把仓库的正式交付当权威，浏览器仅恢复缺失交付；采用已允许的自动化复制时必须绑定请求和会话，识别生成结束/明确结束标记并完整保存。内容一段时间不变化不是答完证明，不能只取第一屏。

现有 no_agent/pre-script 机制可以承载这些脚本；预检查脚本成功时最后一行 `{"wakeAgent":false}` 可省掉模型。不能仅给原来的重型 agent 加这行：有事件时仍需确定性的协调器。附件没有提供 80 多个本机脚本和完整网关分叉，本包不假造这些业务 adapter；必须按 `INTEGRATION.md` 接入既有租约/部署/通知实现后再切换生产任务。

## 7. 会话生命周期与压缩

微信对话身份可以长期不变；模型工作上下文不需要继承 5,600 条历史。将 UI 会话、业务根任务、模型分段三种身份拆开。任务完成后下一个独立任务使用新工作上下文，只携带稳定偏好与适用约束；跨任务事实从状态库按版本读取。

触发整理：任一次最终输入超过 48K；任务边界切换；已完成用户回合达到 20 个或工作消息达到 120 条时检查一次体积（条数只作早期提醒，不当 token 替代）；连续两次整理仍不能把必需工作集压入 64K，则保存胶囊并转受控分段/升级。不能把反复摘要当免费工作。

状态胶囊至少含：task_id、原始目标、不可改变的约束、source_versions、已验证项及证据哈希、待办、已发生/结果不明的副作用、下一批明确动作。预算和租约权威仍在 DB/远端；不要把胶囊里记下的旧租约当当前授权。建议胶囊正文不超过 4K tokens，过大则保留必要约束并把低层证据移入有类型的索引；不可盲截断目标和限制。

内存中的摘要只是检索导航，不是真实状态来源。恢复时核对 source versions、远端租约/completion、实际服务版本和 outbox；已失效的“已验证”不得继续沿用。原始用户目标和约束字段不能被摘要改写，本包会校验它们在 checkpoint 之间保持一致。

原生配置见 `config/native-overlay.yaml`：`compression.threshold_tokens: 48000` 是压缩触发，不是 provider 发送硬上限；`target_ratio` 控制保留尾部，不保证完整压缩后请求固定为某个 token 数。当前官方文档说明 in-place 可归档旧记录而保持会话身份，实际部署版本仍要核对。自动裁剪在完整证据保存和工具组保护未就绪前保持关闭。

## 8. 可靠性红线

必须保留如下证据链，并由确定性提交器控制 completion，而不是模型自述“已经验证”。

1. 操作前身份/版本/权限核验，以及有效消息租约；修改共享资源时再核验资源租约、fence 与 CAS。不能把数据库 local epoch 当作外部系统真正识别的 fencing token。
2. 针对实际改变对象的全量必需测试；成功数量、失败数量、遗漏数量必须对账。测试哈希/部署 SHA 绑定本次产物，旧 PASS 不能复用给新版本。
3. 网络写入超时后的外部事实核对。无幂等键且结果不明的副作用进入人工/可验证恢复，不盲重试，不承诺跨所有系统 exactly-once。
4. 远端回执和 completion 的存在及身份读回、现行 STATUS 协议对账。账本追加需要规定资源租约与 blob CAS；独立新文件不应冒充共享锁的替代。
5. 业务完成与“已通知老板”分开记录；通知进入 durable outbox，只有发送者确认交付才出队。重试/限流期间队列存在，不静默吞掉。
6. 未知类型、证据缺页、输出截断、预算到顶、协议漂移只能进入 WAITING/BLOCKED/ERROR，不能生成绿色 completion。

本包 `finish_local` 只接受当前事件身份、对应源版本、全部 required_checks=true 及远端回执/completion SHA；它验证的是结构契约，真正远端读取和检查执行由受信任提交器负责。不能把模型伪造的一组 true 直接传入它。

## 9. 收益模型及敏感性

以下将同一批业务完成所需输出全部保留，不宣称通过缩短回复省掉它；其他小项按原值保留；额外加 5M gross token 储备覆盖压缩、辅助调用、重试和接入开销。若这些请求已经包含在某个实测桶，验收时只计一次，不能重复累计。

| 输入假设 | 保守 | 目标 | 压力/不达标 |
|---|---:|---:|---:|
| 主会话物理请求保留比例 | 90% | 60% | 100% |
| 主会话平均输入 | 48K | 40K | 64K |
| 收件箱物理请求保留比例 | 80% | 25% | 100% |
| 收件箱平均输入 | 16K | 12K | 24K |
| 主会话 gross | 60.1824M | 34.128M | 88.408M |
| 收件箱 gross | 15.5736M | 4.431M | 28.308M |
| 其他任务原值 | 2.98M | 2.98M | 2.98M |
| 新增开销储备 | 5M | 5M | 5M |
| **总量** | **83.736M** | **46.539M** | **124.696M** |
| **相对 443.90M 保留** | **18.86%** | **10.48%** | **28.09%** |
| 压降倍数 | 5.30 | 9.54 | 3.56 |

例如保守主会话为 `1,357 × 0.9 × 48,000 + 1,560,000 = 60,182,400`；保守收件箱为 `1,137 × 0.8 × 16,000 + 1,020,000 = 15,573,600`。这些是期望量演算，请求数比例可以产生小数，并非声称真的发送了小数个请求。原始数值已有 M/K 舍入，禁止把预测的小数精度解释为测量精度。

分项看：主输入体积由 263.6K 到 48K，单独减少约 81.8%；同桶再减 10% 请求，输入保留约 16.4%，是乘法不是相加。主会话含输出保守减少约 83.2%，收件箱含输出保守减少约 80.9%。其他小 cron 的零模型化虽有价值，但不是达成五倍的主来源。

在保守其他假设保持时，主会话平均输入最多约 52.1K 才接近 88.78M 总阈值；因此把 48K 当平均预算而不是 64K，留出真实工程长尾余量。复杂新任务比例上升、辅助摘要量超过 5M、缓存/计数口径改变，都必须重新预测。

## 10. 实施顺序、重启与回滚

### 阶段 A：不动生产，建立真实基线

在活跃 WAL 上用只读事务取前后快照，按 `session_id, model, billing_provider, billing_base_url, billing_mode, task` 完整键做累计差分。不能用 `WHERE last_seen BETWEEN ...` 对生命周期累计行求和冒充当日用量。新任务记录 root_task_id、每个物理 request_id、辅助调用类型、缓存桶、验证状态、完成时间；Hermes 表中的 `task` 分类不能直接假设等于业务根任务 ID。

本地执行全部测试和 `evidence/recompute.py`。观察器先旁路影子运行，旧任务继续处理；新观察器绝不执行业务副作用。旁路对比至少 100 次扫描和实际代表性事件，包含 HEAD 不变但 retry 到期、自写回执导致 HEAD 改变、源文件新 blob、协议改变、网络失败。

### 阶段 B：把已知脚本路径变成 no_agent

按任务身份而不是按名字猜测定位 jobs.json；迁移前保存实际文件和 ID/调度/工具权限/投递地址清单。不要把附件里的 `?` 当真实 ID。先接入既有 lease、completion 和通知代码，再验证新旧观察/对账结论相同；同一事件执行权仍由唯一现行消息租约裁决。

验证新路径能发现待办、领取、执行、完整复核、回执、完成和通知后，才暂停对应旧 agent 调度。暂停后重读任务状态证明旧路径未继续运行。严禁同时让两个不共享执行权的发送者/部署器上线；systemd/campfire-eval 的重叠职责也要合并到同一事故身份。

### 阶段 C：请求预算与上下文治理接入

使用当前生产 fork 的实际源码定位所有 provider 发送路径，显式接入适配器。先 shadow 记录完整请求计数与 provider usage，验证工具 schema、中文、长日志、推理、输出、重试、fallback、辅助摘要均覆盖；再开硬限制。附带适配器仅支持同步非流式 OpenAI-compatible Chat Completions；现网若使用流式/Responses/Anthropic，需要在该路径完成等价实现及测试，不能绕过准入器。

合并而不是覆盖 `native-overlay.yaml`，保留账号、模型、通道和已有行为配置。当前文档宣称压缩配置可热读，不据此承诺本机分叉一定可热读。代码接入通常需要网关重启：先停止领取新业务、完成或 checkpoint 当前事务、确认补发服务独立存活，再由既有运维流程重启实际 gateway unit。不得自动猜服务名或杀死进行中的外部写入。

若实际 unit 是 `hermes-gateway.service`，使用已确认的用户级服务管理命令重启；恢复后验证微信入站、普通回复、限流 outbox 重试、挂起任务恢复、计量写入和预算拦截。停机时间、进行中任务迁移代价须现场记录；本包没有测量到实际停机秒数。

### 阶段 D：相同工作量验收

用至少 30 个匹配复杂度、检查集合和交付要求的已完成任务做配对/影子回放，另观察至少 72 小时运行长尾；样本量是初始门槛，不是统计证明。副作用不可双执行，回放仅在隔离环境，线上用单执行者。

**同时满足**：同等 accepted work 的总 gross≤20%；所有模型/压缩/失败重试/分段计入；验证集合未减少且无假 PASS；通知/消息不丢；重复业务副作用为零；pending/BLOCKED 数量没有通过延期完成而持续堆积；预先约定的完成和通知延迟 SLO 没有退化。只比较“一天花多少”而让任务少做一半，不算省 token。

如果可靠性/完成率/SLO 未达标，回退对应预算或执行路径，保留新产生的状态记录与幂等身份；不要删预算库、completion 或 outbox 来“干净重来”。继续报告压降尚未达标，不能用可靠暂停当作可靠完成。

## 11. 源码交付边界

本包包含预算持久化、证据存储、完整工具组压缩、只读批量执行、事件去重/本地 fence、通知 outbox、计量快照差分、零模型 Git 观察器、同步 provider 适配器、无 checkout 的 Git 发布脚本，以及本地 67 项测试。

它不是修改过的完整 Hermes fork，也不是已经接好现网所有 cron 的一键升级器。未提供的本机脚本、浏览器状态、实际费率、在线 tokenizer 和流式路径都不能凭空替换。`INTEGRATION.md` 指定的连接点完成前，不能关闭旧生产路径或宣布五倍目标实现。

给老板的解释：**检查一项都不删。固定检查让程序一次做完，只有真正需要判断时才叫模型；模型每次只看这件事需要的材料。超限任务不会丢，也不会冒充完成，而是带证据继续处理或可见升级。最终以相同工作完成量、相同验证标准和实测 token 判定。**
