# 扩展与数据契约（v2）

## 1. 单一事实源

正式数据是 `data/recipes.json`。`index.html` 是构建产物，不直接编辑内嵌JSON。浏览器导出菜谱库也可编辑后导入；导入仅影响当前浏览器保存的库，不会自动改磁盘源码。

运行 `node tools/check_catalog.mjs` 做语义校验；JSON Schema是编辑器结构提示，不替代运行时的跨引用、模板和采购组校验。正式菜谱不允许 `choices` 或材料行 `optional`。

## 2. 原料层

`ingredients` 按稳定英文ID组织。字段：`name / unit / group / storage / note / allergens[]`，可带 `freshHerb / pantryHint / purchase`。

单位只允许 `g / ml / tsp / 个 / 张`。不要在同一ID里混g和ml。干迷迭香与鲜迷迭香是两个食材ID，不能“同一种香草”一并采购。已煮熟、是否即食会影响保存与烹饪，必要时也必须独立ID。

`pantryHint` 是“可能已拥有”的显示提示，计算时绝不偷偷扣除库存。

### purchase换算

`yield`表示一个采购单位能提供多少当前原料单位，`roundTo`表示采购步长，`method`控制同采购ID的合并。

- `max`：同一颗柠檬提供汁与皮屑，先各算需要多少颗，再取最大。
- `sum`：做蛋饼用的蛋液与窝蛋要消耗不同鸡蛋，因此相加。
- 生米采购属于熟米饭的估算换算，显示在“采购折算”而不是净材料清单重复一行。

同采购ID必须统一名称、单位、算法、取整步长。每种原料的yield可不同，例如柠檬汁与皮屑。程序保留每个组成需求作为依据。

## 3. 菜谱层

稳定 `id` 用于保存菜单、笔记、迁移；`revision`在实际配方改变时增加；库发布提高 `version`。换标题不等于必须换ID；完全不同菜不应悄悄占用旧ID而不写迁移告知。

核心字段：

| 字段 | 契约 |
|---|---|
| `basePeople` | 本菜基准人数，内置均为2 |
| `ingredients[]` | 每条有key、ingredient、qty、form、stage、pack、scaling |
| `key` | 本菜内唯一，供步骤模板引用，不等于食材ID |
| `form` | 精确形态：切片、拍裂、细末、已蒸熟、净重等 |
| `stage` | 在家或现场，是材料处理阶段，不表示菜已经完成 |
| `pack` | 本菜内部的分装组，不跨菜合并，不混生熟 |
| `scaling` | linear随食客份量；batch随锅／批次 |
| `steps / prep` | 现场动作与家里准备；引用用 `{{材料key}}` |
| `decisions` | 逐道明确为什么选鲜／干／成品和该加入时机 |
| `profile` | 可共享的味型标签，切勿每道硬造唯一味型 |
| `texture` | 给用户看的具体口感描述 |
| `textureFamily` | 共同结构分类；多道相近口感合并统计，≥3道提醒 |
| `technique` | 设备／动作大类，不是一个漂亮名称 |
| `taste / moment / fun / why` | 吃到什么、参与方式、与其他菜的实质区别 |
| `activeMinutes` | 单基准批次的现场主动操作估计 |
| `totalMinutes` | 单批从开始做到出餐的占用估计，≥activeMinutes |
| `homeMinutes` | 在家任务逐项准备估计，不隐藏蒸煮等前置劳动 |
| `batchFactor` | 一批最多装多少基准份；内置1，不假设烤炉能无限扩大 |
| `rich / light` | 人工审查标签，不是营养学结论 |
| `needsFreezer` | 明确要求持续冷冻的菜，例如冰淇淋 |
| `sources[] / origin` | 技法来源及露营改编边界，不表示克数已实测 |

`scale = people / basePeople × portion`；`batches = max(1, ceil(scale / batchFactor))`。

线性材料 = 基准量×scale；按批材料 = 基准量×batches。家庭和现场时间按完整批次估计，半份也不会把一次翻面和预热变成半次。不得把临界锅底水做成线性材料；也不得把实吃调味料随锅容积随意放大。

步骤中的料量必须用模板，不能把“10g”写死后让配料表缩成5g而步骤仍10g。温度、厚度、每批时间与锅具最小尺寸是操作约束，不随人数放大。

## 4. 菜单审查与新鲜感

`reviewMenu`是可解释启发式，不是厨师评分模型：识别味型、共同口感、主材重复；主动操作>65分钟、≥3道浓味、≥4道缺清爽、≥4种鲜叶、>7道等给提示，不禁止用户选菜。

互补建议综合不同味型／口感／技法、现有材料复用、工作量与最近3次记录；不会自动增菜。阈值和权重都在纯引擎中，可以直接修改并补测试。照片、华丽标题、同一道换粉不能作为“新玩法”的验收依据。

8套菜单只是经过人工组合的起点；顺序按rank，可手动上下调整。没有对真实炉面进行并发调度，也不根据人数承诺固定完成时刻。

## 5. 状态与迁移

`defaultState`负责默认结构；`sanitizeState`限制人数、选菜数、文本大小并清理未知ID。更新配方／份量使相关signature变化，备料和步骤的旧勾选失效，笔记保留。signature仅为确定性变化标记，不是密码学签名。

v2完整备份包含库；导入前先校验其中的库，再恢复状态。v1备份不把旧鲜干菜谱库注入v2，只读取选菜、份量、人数、笔记。`migration.retired`列出退役项；suggestedId只显示建议，不自动替代。`migration.rewritten`要求使用者重新审阅。

导入限制5MB；未通过校验不覆盖现有库。无eval或模板代码执行。输出HTML文本转义；外链只接受http/https且不含凭据；CSV首字符公式转义。该程序不是不受信任大规模内容的托管平台。

## 6. 新增或修改的验收顺序

1. 先明确味型、口感组、值得做的动作，与已有菜有什么区别；没有区别就合并。
2. 选择稳定材料形态，并把来源只绑定到真正支撑的技法；数量注明露营改编。
3. 检查食材每条数量、预制和现场是否引用同一份，生熟分装、冷链、锅底水与熟度是否闭合。
4. 给0.5份、1份、多人批次跑 `recipeView / buildPlan`，检查购物清单和步骤一致。
5. 涉及新单位／采购规则先改引擎和测试；不要在UI里补一条临时换算。
6. 运行validate、单元、构建和浏览器测试，再覆盖发行HTML；更新版本、审查记录与测试报告。

源码不依赖框架构建链。Python打包器只剥离当前一条静态import与顶层named export；引入更多模块时必须升级打包器，不要绕过其保护。
