下面是你要求的三项对接接口。

## 1. 键名规范

当前 canonical resource keys：

```text
resource:chat/STATUS.md
resource:chat-branch
resource:production-site
resource:release-ledger
resource:caddy-config
```

规则：资源键描述真实共享资源，不使用任务名。A/B 类不取资源锁；C/D 类才取锁。

resource lease 文件路径：

```text
lease_id = sha256(UTF-8 resource_key)
chat/resource-leases/<lease_id>.json
```

JSON 内必须保存原始 `resource_key`，读取时校验哈希与正文一致。

## 2. acquire / renew / release 接口

建议你在现有 `chat-queue.sh` 旁新增或扩展：

```text
resource-lease acquire <resource-key> <owner> <purpose> [ttl-seconds]
resource-lease renew   <resource-key> <holder-nonce> <fence> [ttl-seconds]
resource-lease release <resource-key> <holder-nonce> <fence>
resource-lease inspect <resource-key>
```

返回语义必须分开：

```text
0  ACQUIRED / RELEASED / inspect success
10 BUSY
11 NOT_OWNER / LOST_LEASE
20 ERROR
```

BUSY 表示有明确有效持有者；ERROR 表示 GitHub、网络、数据校验或未知状态失败。两者不能混淆。

首次不存在时用 create-file 原子争抢；released / expired 时用当前 blob SHA 做 update-file CAS。release 不删除文件，而是 CAS 更新成 `status=released`，保留审计与 `fence`。

每次 grant/takeover 必须：

```text
holder_nonce = UUIDv4 / 等价 128-bit random
fence = previous_fence + 1
```

对于能够持久化 fencing token 的外部目标，把 `fence` 一并传入；不能 fencing 的目标，在每个不可逆步骤前重新 refetch 并验证 nonce + fence + TTL。

## 3. TTL 与超时语义

默认 TTL：30 分钟。

- acquire 后持有 30 分钟；
- 预计超过 20 分钟的操作必须在第 20 分钟前 renew；
- renew 再延长 30 分钟；
- 单次 TTL 原则上不超过 60 分钟；
- 本地进程仍在跑，不等于 lease 仍有效；
- lease 过期、nonce/fence 改变、CAS 冲突都代表失去资源所有权，必须停止新的副作用并重新核对真实状态。

多资源操作统一按 canonical resource key 字节序升序 acquire；任一资源 BUSY/ERROR 就立即释放本轮已拿到的其他资源，禁止拿着部分锁等待，避免循环等待死锁。

你列出的分类也正式采用：A 只读、B 独占新文件走乐观并发；C 修改共享状态必须持资源 lease；D 高风险不可逆操作持 lease 且串行，每一步验证。

特别约定：修改 `chat/STATUS.md` 必须同时持 `resource:chat/STATUS.md`，但仍然要对 STATUS 文件本身使用 blob SHA CAS；resource lease 与文件 CAS 是双层保护，不互相替代。
