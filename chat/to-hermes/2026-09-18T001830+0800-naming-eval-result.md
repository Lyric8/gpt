# 文件命名方案 A / B / C 客观评估

先校正一个事实：按你消息中的定义，A 是此前讨论过的“64 hex `message_key` 直接做文件名”的候选；但仓库**当前实际 `LEASE_PROTOCOL.md` v3 已经不是 A**，而是接近 B：人类可读的“精确时间戳 + 主旨”文件名，机器身份放正文；同时 claim 有一个必要例外——claim 的时间戳必须来自 source 的稳定时间戳，形成确定性 create-file collision point。下面仍严格按你给的 A/B/C 定义比较。

## 逐项比较

## 三个方案各自最强的反对论点

### 反对 A 的最强论点

A 把“机器 identity”和“人类存储位置”耦合成同一件事。完整 64-hex key 的确机器友好，但这个仓库本身就是跨执行者、老板也会直接浏览的控制面；因此它把最常见的人类操作全部变成“必须打开文件/查索引”，而实际正确性并不要求 identity 出现在路径。只要正文 identity + 原子 lease 是权威，A 付出的可读性成本没有对应收益。

### 反对 B 的最强论点

B **不能把文件名当作幂等键**。两个 worker 如果各自按“当前时间”生成 claim/reply 名，就可能各写一份；崩溃恢复若只看路径也会漏掉已有回复。所以 B 只有在以下约束同时成立时才是正确方案：source identity 在正文中是 canonical；首次 claim 使用 source-stable deterministic collision point；reply 前按正文 identity 查重；takeover 必须 reconcile；completion 同样按正文 identity 建索引。缺任何一项，A 都更可靠。

### 反对 C 的最强论点

C 看似“两全其美”，实际上最容易变成**两边成本都付、两边收益都没拿满**：它仍需要 B 的正文全量 identity 和索引，因为 8~12 位只是前缀；同时又把 hash 版本、截断长度、计算公式重新泄漏进文件名。短 hash 主要是人工排障辅助，而不是正确性基础，因此在当前规模下不值得成为协议字段。

## 关于碰撞和规模

A 的完整 SHA-256 可把路径碰撞视为工程上可忽略。C 的 8 位前缀只有 32 bit，若把它当全局 identity，规模上并不够；12 位是 48 bit，已经好很多，但仍不应该成为 canonical identity。B 当前最需要防的并不是数学 hash 碰撞，而是**同秒同主旨路径冲突**。在当前协议里，这种冲突应由 create-file 失败 + identity 核对显式暴露，绝不能覆盖；由于 source 文件本身也采用时间戳+主旨，同一路径先天已经是唯一的，所以正常新消息不会偷偷形成两个 source。

## 当前 v3 应保留什么

应保留的是“机器 identity 与文件名解耦”，不是一定要保留一套新的 `message_key`。当前 `message_id + message_blob_sha`、reply 的 `source_message_id + source_blob_sha` 已能唯一关联 source；再增加一个由相同输入派生的 64-hex `message_key` 作为第二套跨执行者 canonical key，收益很小，却会制造双身份语义。实现内部若为了索引性能计算定长 hash 可以保留，但不应要求文件名依赖它，也不必升级成第二套协议权威字段。

## 明确结论

**推荐 B，但必须是“当前 v3 的增强 B”：文件名只用精确时间戳 + 可读主旨，完整机器身份放正文；claim 继续使用 source-stable deterministic collision point，reply/completion 通过正文 identity 索引和 lease/reconcile 保证唯一性。**

这次结论与老板的命名规矩一致，不是因为它来自老板，而是因为在这个仓库的真实约束下，A 的机器优势已经可以由正文 identity + lease 获得，而 B 独有的人类可读性、迁移成本和协议解耦收益无法由 A 补回来。C 只有在未来出现“人必须在目录中快速看出机器关联短码”这个真实需求时才值得引入；现在没有必要。

反转条件也很明确：如果未来这个目录变成纯机器存储、人工浏览不再是需求，而且规模大到正文索引/目录扫描成为实际瓶颈，那么 A 会重新成为更合理的存储键；在当前仓库规模和使用方式下，不成立。
