# 已确认：GPT 侧工作默认连接器直推，失败只允许一次有依据重试

收到并采用这套口径。以后只要任务目标是 GitHub 仓库内可直接落地的代码、配置、文档或分支操作，我这侧的默认路径是：**先用已连接的 GitHub 写能力直接完成分支/文件/提交/推送闭环；不把“让 Hermes 代推”当默认方案。**

## 连接器失败时的固定自查清单

我会按下面顺序做一次完整自查，然后只重试一次；不会在第一次失败后直接下结论说“连接器只读”或“网络不通”。

1. **工具与能力选择**：确认调用的是 GitHub connector 的写操作，而不是误用只读搜索/网页抓取；先检查当前会话实际暴露的写 schema，确认 create/update/branch/commit 等能力是否存在。
2. **仓库与分支**：核对 `owner/repo`、目标分支名、分支是否真实存在；需要新分支时先确认是否已经创建成功，避免把“分支不存在”误判成权限故障。
3. **路径语义**：核对目标路径、大小写、编码与父目录；创建文件前确认路径不存在，更新文件前先读取当前 blob SHA，禁止拿旧 SHA 盲写。
4. **并发与 CAS**：若是 `409/422`、SHA conflict、目标已存在等冲突，重新读取最新 branch head / blob SHA，判断是并发写入、重复创建还是路径状态已经变化；只有确认属于瞬时竞争才按最新状态重试。
5. **认证与权限**：区分“仓库不可见”“分支不可写”“具体 endpoint 不在 connector allowlist”“连接器认证失效”这几类错误，不把不同原因统称为网络问题。
6. **调用参数**：复核 branch/ref、sha、message、path、content 等字段是否符合该 connector 的真实 schema，尤其避免把 REST API 原生参数想当然地套到 connector wrapper 上。
7. **多文件工程交付**：优先使用当前连接器暴露的最高层级原子/批量写能力；若只能逐文件写，则保证同一路径串行、每一步基于最新状态，并在目标开发分支提交，`chat` 分支只留交接文档。
8. **结果核验**：写调用返回成功后，再读取 branch/file/commit 验证目标状态，不把“API 返回成功”单独当成交付完成。

## 唯一一次重试规则

自查发现明确可修正问题后，我会刷新最新仓库状态并重试一次。第二次仍失败，或者错误本身属于明确的权限/安全策略/connector 能力边界，就停止继续撞接口，避免制造半成品或重复提交。

## 第二次仍失败时的交付规则

我会在当前回复中同时给出：

- 已完成的完整源码/方案，不留“请你自己补”的缺口；
- 可点击下载的完整交付物；
- `SHA256SUMS`（多文件包必须有）；
- 可直接执行的测试/验收入口与我已运行的结果；
- 目标仓库、目标分支、预期落点；
- connector 原始失败类别、我做过的自查项、唯一一次重试结果；
- 明确区分 `PUBLISHED / NOT_PUBLISHED / DEPLOYED / NOT_DEPLOYED`，不把“代码已打包”说成“已上线”。

这套规则以后作为 GPT 侧 GitHub 工程交付的默认施工纪律执行。
