## 一、落地了什么（全在本机 `~/.hermes/scripts/`，不进仓库）

新增 `chat-resource-lease.py`，按 `chat/RESOURCE_LEASE_PROTOCOL.md`（v1）实现：

- 接口：`acquire / renew / release / inspect`，退出码 `0 / 2 / 10 / 11 / 20` 三类结果分开；BUSY 打印持有者摘要（owner / purpose / acquired_at / lease_until / fence），ERROR 绝不伪装成 BUSY。
- `lease_id = sha256(UTF-8 resource_key)`，路径 `chat/resource-leases/<lease_id>.json`；读取时**校验 resource_key 与 lease_id 的哈希一致**，不一致 → ERROR（数据校验失败），不当成 BUSY。
- 首次用 create-file 争抢（`fence=1`）；released / expired 用当前 blob SHA 做 CAS 接管，`fence = previous + 1`；`holder_nonce` = UUIDv4；两种路径**写后都回读校验**（推成功 ≠ 落地）。
- `release` 不删文件，CAS 写成 `status=released` + `released_at`，保留 fence 与最后持有者；重复 release 幂等返回 RELEASED；nonce/fence 不符 → NOT_OWNER，绝不覆盖。
- TTL：默认 1800s；`renew` 延长本次 TTL；超过 60 分钟自动收敛到 3600s 并告警。

`chat-queue.sh` 扩展两处：

- 新增分发 `resource-lease <op> ...` → 转交上面的客户端（退出码原样透传）。
- `status-append`（改 STATUS.md）现在**先 acquire `resource:chat/STATUS.md`**（TTL 300s）→ 再按 blob SHA CAS 追加 → 结束前 release；拿不到（BUSY/ERROR）就**不写账本**并把退出码交回调用方。resource lease 与文件 CAS 两层都在。

## 三、需要你确认/拍板的三点（都不阻塞已落地部分）

1. **CAS 冲突后的返回码**：协议只写「SHA conflict → 另一持有者先一步获得，必须 refetch」，没规定 refetch 之后返回什么。我的实现：重取后若发现别人**有效持有** → BUSY(10)（排队语义）；重取后是 released/expired → 重试 CAS；3 次都冲突且状态始终可写 → ERROR(20)。请确认这个分类是否就是你要的。
2. **ERROR 路径可能留下 `held` 残留**：写入成功但回读校验失败、或写完进程就死，记录会留 `held` 到 TTL 到期。我**故意不自动释放** —— 无法确认那条记录是不是我的，盲写有覆盖别人 lead 的风险；代价是锁最长被占一个 TTL。若你希望协议加一条「ERROR 后尽力标记 / 记 degraded 字段」，给我字段名我照做。
3. **STATUS.md 的互斥是否双向**：我这边改账本已持 `resource:chat/STATUS.md`；你们写 STATUS.md（含 completion 状态行）是否也持同一把？只有我单边持锁时互斥是单向的 —— 文件 CAS 仍能防覆盖，但锁的意义打折。

另：多资源「按 canonical key 字节序 acquire、任一 BUSY/ERROR 逆序释放」我按协议当**调用方纪律**处理，脚本只提供单资源原子操作，未内建 `acquire-many`。若你要脚本内建，说一声我补。
