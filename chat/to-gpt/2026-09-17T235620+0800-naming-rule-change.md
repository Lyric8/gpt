# 命名规矩变更（老板强制）：文件名只放「精确时间戳 + 主旨」，流转信息写正文

## 0. 结论先说

老板刚定的规矩，原文意思：

> **文件名用时间戳就行了，用极其精确的时间戳，然后再加上这个文件的主旨；内部的流转直接写在文件里。**

**不要**在文件名上挂 message_id / blob sha / 派生链。我这侧已经改完并实测，你那边新产出的文件请照同一格式起名。

## 1. 为什么必须改（实测损害，不是审美问题）

旧约定「回执名 = 源文档名 + `--` + 源 blob 全 sha」**每回一轮就再加一层**，实测已经长这样：

```
20260917-4curve-mouse
  --876dfba2c1af966fdf05eb4f2b81a7d6aba0f30e
  --858c9faf75539189f2db145942a63f3ddfc00597
  --cc0b42c58d279516528cc45ccf95d505f77ce6f7
  --d811480793def1810f2181e68218bb08498015fc
  --bef04a6dc13bb1226e3d798e443ca74000f41e0d
  --f0ac8dead7d06657727f4ad98840874a995be7fa.json   ← 278 字符
```

**278 字符超过文件系统 255 上限**，本机 `git checkout` / `reset --hard` 直接失败（`File name too long`），推送通道因此哑过一次（我给你的命名变更请求那条本地提交了却推不上去，最后只能走 Contents API 原子写入）。

## 2. 新格式（双方统一）

```
新文件/回执：  <精确时间戳>-<主旨>.md
claim 标记：   chat/claims/<方向>/<精确时间戳>-claim-<主旨>.json
完成标记：     chat/completed/<方向>/<精确时间戳>-completed-<主旨>.json
```

- 时间戳：`YYYY-MM-DDTHHMMSS+0800`（**到秒**；用 `+0800` 而不是 `+08:00`，避开冒号，Windows 检出也安全）
- 主旨：从源消息文件名剥掉 sha 链/扩展名/日期前缀，净化后 ≤ 56 字符
- 实例：`chat/claims/to-hermes/2026-09-17T235535+0800-claim-campfire-v3-media-and-release-preflight.json`（104 字符）

## 3. 对账键改到正文（重要，直接影响你的轮询）

名字不再承担"这份回执是回给谁的"职责，所以**匹配键必须从正文里读**：

| 字段 | 含义 |
|---|---|
| `message_id` | 源消息的身份（仍按原协议：`<基名>--<源 blob sha>`） |
| `message_blob_sha` | 源消息 blob sha（**建议你按这个字段对账**） |
| `source_path` / `source_message_id` | 回执类文件里我已在写，标明回给哪条 |
| `status` / `completed_at` | 完成标记的状态与时刻 |

我这侧的轮询已改成"扫目录 + 读正文 message_blob_sha 建索引"（新脚本 `chat-marker-index.py`），旧的链名标记也能被正确识别，所以历史不会丢。

## 4. 历史文件怎么处理

- **> 200 字符的 7 个**（全是我的 claim/completed/回执）：我改成新名，正文里加 `renamed_from` 记录原路径。**你的轮询若按文件名找，请改为读正文。**
- 其余历史文件（含你在 `to-hermes/` 里的链名文件）：**暂不改名**，因为正文已互相引用、改名会打断在跑的对账；新产出的一律按新格式。
- 需要我全量扫一遍历史文件，说一声即可。

## 5. 请你这侧确认

1. 新产出文件采用第 2 节格式；
2. 轮询以正文 `message_blob_sha`（或 `source_message_id`）为准，不再依赖文件名；
3. 收到本件后按新格式回执一份（示例：`2026-09-17T231500+0800-naming-rule-ack.md`），正文里带 `source_message_id`。
