**四条要特别注意的：**

1. **SSH 对公网开着，但没人能进。** 22 端口可达，可 `~/.ssh/authorized_keys` 是**空的（0 个公钥）**。也就是说现在没有任何密钥能免密登录。要用 SSH 做部署，**必须先由我装公钥**。
2. **云安全组我改不了。** 那是腾讯云控制台，只有老板能操作。你的方案若需要新开端口，必须走老板，这会有额外交接成本 —— 尽量复用已有的 22/80/443。
3. **出网到 GitHub 是"部分稳定"。** 实测 `api.github.com` 很快（0.27s），`codeload.github.com` 正常；但 **git 协议（clone / push / fetch）今天断过好几次**，报 TLS 连接被中断、连 443 超时。所以「谁来主动发起连接」这件事值得纳入设计：让 GitHub 主动连进来，比让这台机器主动连出去更稳。
4. **这台机器上还跑着别的东西**（上面那两个端口）。改动请不要影响它们。

## 二、部署这一段现在怎么跑

`projects/campfire-kitchen/deploy/release.sh`，在项目目录里执行，七步：

1. 项目完整性检查（关键文件缺一个就停）
2. 数据与引擎测试（`check_catalog` + 105 项单测）
3. 构建 `index.html`
4. **哈希闸门**：本机构建出的产物哈希必须等于 `SHA256SUMS.txt` 的登记值，不等就停
5. 安装产物到 `/var/www/campfire-kitchen/index.html`
6. `systemctl reload caddy`
7. **线上实测**：拉一次本机 HTTP，比对返回体哈希、校验 `nosniff` 头、确认目录列表未开放

特性：非交互、失败即停、幂等（重复执行无副作用）。现在的触发方式是**我在服务器上敲一条命令** —— 这是过渡形态，你的任务就是把它换成"发版触发"。

## 三、两条可行通道与取舍

| | 推式：GitHub → 服务器 | 拉式：服务器 → GitHub |
|---|---|---|
| 原理 | Actions 跑到部署步骤时主动连进服务器 | 服务器上的定时任务轮询 GitHub，发现新版本就部署 |
| 需要的凭据 | 一把 SSH 部署私钥（存 GitHub Secrets）+ 服务器上装对应公钥 | 一个只读 token（或干脆匿名读公开仓库） |
| 对公网暴露 | 需要 SSH 入口（已有） | 不需要对公网开任何东西 |
| 触发延迟 | 点完立刻开始 | 要等下一个轮询周期 |
| 依赖哪边的出网 | 不依赖服务器的出网质量 | **依赖服务器的出网**（见上面第 3 条，今天不稳） |
| 常驻需求 | 无 | 服务器上要有个常驻的计时器/服务 |

**如果让我选，我选推式**，主要因为这台机器连 GitHub 不稳定，而 GitHub 的 runner 连进来没有这个问题。**但这个决定权在你**，你要用拉式或别的形态，我只要求你把第三条通道的凭据需求写清楚，我来备。

> **2026-09-17 实测补充：拉式方案在本机不可行。** 真实下载一个 GitHub release 资产，90 秒超时、收到 0 字节；`raw.githubusercontent.com` 也连不上。所以产物必须由 GitHub 侧经 SSH 送进来。详见 `2026-09-17-deploy-boundary.md` 第一节。

## 四、若选推式，我建议的形态（供你参考，不是要求）

- 建一个**专用账号**，不给交互式 shell —— 那把钥匙能部署，就不该同时能开一个 shell 到处逛
- 公钥装进那个账号，并加上限制（来源、限定只能执行部署入口）
- **密钥对由你生成**，只把**公钥**给我装：这样私钥从头到尾不经过我，直接进 GitHub Secrets，各方都干净
- 部署入口定成**一条非交互命令**（`release.sh` 本身就满足这个性质）

## 五、服务器侧我能做什么

**能做**：装公钥、建账号、装软件（apt / npm / pip）、改 Caddy 与其他 systemd 配置（备份 → 校验 → reload）、执行部署、回滚、看日志、验证可达性、跑一次性脚本。

**做不到**：改腾讯云安全组、买域名、备案。
