## 二、目标

把发布变成**「在 GitHub 上正式发版，才部署」**：

1. 平时往 `main` 推代码 —— **线上不受任何影响**
2. 只有在 GitHub 上**发布一个 Release**（带版本号、带成品、带说明）时，才触发部署
3. 这次发版要产出**可下载的成品** —— 这个项目是离线优先的单文件静态应用，构建产物本身就是可交付物，别人下载一个文件就能用
4. 一个版本对应一份成品、一份部署记录：事后查得到、回滚得了

---

## 三、不能破的约束

1. **不能出现「push 即上线」。** 这个项目的中间态代码经常是残的（源码没传完、测试没过）。线上只接受「被正式发版」的东西。
2. **发布失败不能破坏线上。** 任何一步不过，线上必须还是上一次成功的版本。
3. **密钥不进仓库。** 部署凭据只存在于 GitHub Secrets 与服务器侧，不进任何被提交的文件。
4. **仓库结构规矩不能破。** 根目录不是部署目录；项目根永远是 `projects/campfire-kitchen`；项目自己的 `README.md` 是操作契约。新增文件放进合理的位置。
5. **服务器侧的动作归 Hermes。** 你设计，但需要服务器上做什么（放公钥、装依赖、改配置、开端口），写进 `chat/to-hermes/`，由 Hermes 执行。不要假设你能在服务器上执行命令。
6. **不要动 `chat/` 里已有的文档**，也不要替 Hermes 做服务器侧的决定。

## 四、需要你拍板的设计决策

不用问老板，你定；定了在文档里写清理由。

1. **`index.html` 以后还提不提交进仓库？** 现在它提交了，并且被 `SHA256SUMS.txt` 登记哈希；`deploy/release.sh` 会拿构建产物跟这个登记值比对，用来防止「源码与产物不同步」。如果改成发版时由流水线构建，仓库里那份就成了重复产物，这道闸门要跟着改 —— 否则要么形同虚设、要么天天拦住发布。选一个方向并说明理由。
2. **构建发生在哪里。** 在服务器上构建，还是在 GitHub 的 runner 上构建后送过去。国内网络条件值得纳入考虑。
3. **部署通道怎么走。** 服务器 SSH 端口对公网是通的；`~/.ssh/authorized_keys` 目前是空的（Hermes 确认过，需要放公钥时由 Hermes 执行）。
4. **成品以什么形式挂到 Release 上**，以及版本号与 `package.json` 的 `version` 怎么保持一致。
5. 要不要保留 `deploy/release.sh` 作为「人工兜底通道」（流水线不可用或需要紧急发布时使用）。

## 五、验收标准

做到下面全部，这件事才算成：

- [ ] 往 `main` 推一个提交，线上返回的内容**没有任何变化**（有可检验的证据）
- [ ] 在 GitHub 上发布一个 Release，部署**自动发生**，过程在 Actions 日志里看得见
- [ ] 这个 Release 上挂着**可下载的成品**，下载下来就是能直接打开使用的应用
- [ ] 故意让校验失败（例如改坏一个测试或让哈希对不上），发布**被拦住**，线上仍是上一版
- [ ] 线上返回的内容与这个版本构建出的产物**逐字节一致**（给出哈希证据）
- [ ] 发布历史可查：哪个版本、什么时候发的、发的是哪个文件
- [ ] 回滚有明确路径，并且**实际验证过**
